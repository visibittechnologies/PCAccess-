JavaScript (MyAppjs) Pattern - **Never write inline scripts inside `.cshtml` views.** - All JavaScript must be placed inside dedicated files in `MyAppjs/` matching the feature domain (e.g., `MyAppjs/Device/device.js`, `MyAppjs/Folder/folder.js`, `MyAppjs/Common/`). - **AJAX & Response Pattern:** - Strictly follow the existing AJAX response contract: ```javascript $.ajax({ url: '/ControllerName/ActionOrAPI', type: 'POST', data: JSON.stringify(postData), contentType: 'application/json; charset=utf-8', dataType: 'json', success: function (res) { if (res.status === 'success' || res.status === 1) { // Success handling using existing notification pattern (toastr/sweetalert) } else { // Error message handling using res.msg or res.message } }, error: function (xhr, err) { // Standard error handling } }); ``` - **Reusability:** Always check and reuse existing common JS files (`MyAppjs/Common/master_dataTable.js`, `Common.js`, `modal.js`, `drawer.js`) before writing custom DOM logic. - **Comments & Reason:** Every function must have JSDoc/comments stating its purpose, trigger event, and rationale based on existing project flow. --- ## 2. Views & UI (Razor & Tailwind CSS) Pattern - **Layout:** All admin/portal views must inherit from `~/Views/Shared/_Admin_Layout.cshtml`. - **Design System:** - Follow the existing Tailwind CSS configuration strictly. - Brand colors: Emerald Primary (`#1f9251` / `text-primary` / `bg-primary`), Slate typography, soft neutral borders (`border-slate-200/80`). - Font: `Manrope`, sans-serif. - Icons: Lucide Icons (`data-lucide="..."`) as already imported in the layout. - **Components:** - Reuse existing card structures, table headers, status badges, and button styles. - Never introduce another CSS library (No Bootstrap overrides, no Tailwind plugins not in layout, no ad-hoc stylesheets). - Maintain responsive layouts across Mobile (`<640px`), Tablet (`640px-1024px`), and Desktop (`>=1024px`). - **Comments & Reason:** Include Razor comments (`@* ... *@`) at the top of sections explaining the component's role and layout alignment. --- ## 3. Models & ViewModels Pattern - Models must reside in `PCAccess.Models` or appropriate sub-namespaces. - Property names must match database column conventions and stored procedure parameters. - Use standard data annotations (`[Required]`, `[StringLength]`, `[Display]`) consistent with existing models. - For tables, searches, and data grids, strictly use the existing pagination models (`JqDataTableModel`, `SearchModel` in `TablePagging.cs`). - **Comments & Reason:** Document model properties with C# XML doc comments (`/// `) indicating which database table/SP/View they map to. --- ## 4. Controllers & APIs Pattern - **Controllers:** - Inherit from standard `Controller`. - Controllers must remain **thin**: orchestrate requests, validate input, call `BAL`, and return standard responses. - Business logic strictly belongs in `PCAccess.BAL/`, NOT inside the controller. - **APIs & AJAX Endpoints:** - Any new API MUST be built on the existing API controller pattern (e.g., `AccountAPIController.cs` or `[Feature]APIController.cs`). - All JSON endpoints must return the standardized response structure: ```csharp return Json(new { status = "success", // or "error" msg = "Descriptive user message", data = resultObject }, JsonRequestBehavior.AllowGet); ``` - Authentication and session checks must strictly use `CommanUtilities.Provider.GetCurrent()`. - Unhandled exceptions must be caught and logged using `ExceptioLoggerDB`. - **Comments & Reason:** Every Action/API method must specify HTTP verb, input contracts, return structure, and business justification. --- ## 5. Business Access Layer (BAL) & Data Access Layer (DAL) Pattern - **BAL (`PCAccess.BAL`):** - Classes like `DashboardManager.cs`, `ActivityLogHelper.cs`, etc. - Contain all business validation, logic flows, and data mapping. - **DAL (`PCAccess.DAL`):** - All database execution goes through `PCAccess.DAL.MySqlHelper` and `PCAccess.DAL.Parameters`. - Methods: `ExecuteDataTable`, `ExecuteNonQuery`, `ExecuteScalar`. - Connection string must ALWAYS be read from `ConfigurationManager.ConnectionStrings["constr"].ConnectionString`. - **Comments & Reason:** Every BAL method must document parameter validation rules, SP invocation target, and return data structure. --- ## 6. Stored Procedures (Doc/Procedure/) Pattern - Every Stored Procedure must be stored in an individual `.sql` file under `Doc/Procedure/`. - Script header must always specify: ```sql USE [PCAccess_DB] GO ``` - **Standard Naming Convention:** `proc__` (e.g., `proc_device_list`, `proc_device_insert`, `proc_file_access_log`). - **Mandatory Parameter Pattern:** ```sql CREATE PROCEDURE [dbo].[proc_device_list] @ActionType INT = 1, @device_id INT = NULL, @status VARCHAR(50) = NULL OUTPUT, @msg NVARCHAR(255) = NULL OUTPUT AS BEGIN SET NOCOUNT ON; BEGIN TRY -- Procedure body SET @status = 'success'; SET @msg = 'Data retrieved successfully.'; END TRY BEGIN CATCH SET @status = 'error'; SET @msg = ERROR_MESSAGE(); END CATCH END ``` - Output parameters `@status` and `@msg` are mandatory for all operations. - **Comments & Reason:** Include a header comment block in every `.sql` file explaining Author, Date, Purpose, ActionTypes, and Calling Method in BAL/DAL. --- ## 7. Database Tables (Doc/Table/) Pattern - Every table creation script must be saved as a separate `.sql` file in `Doc/Table/` (e.g., `tbl_device_master.sql`). - Must start with `USE [PCAccess_DB] GO`. - **Standard Audit Fields:** - `id INT IDENTITY(1,1) PRIMARY KEY` - `created_at DATETIME DEFAULT GETDATE()` - `created_by INT NULL` - `updated_at DATETIME NULL` - `updated_by INT NULL` - `is_active BIT DEFAULT 1` - `status VARCHAR(50) DEFAULT 'active'` - **Comments & Reason:** Include comments on each column and table definition documenting primary/foreign key relationships. --- ## 8.
